# 0016 — Define one guide format, and build every guide's PDF from it

- **Status:** Accepted
- **Date:** 2026-10-24

---

## Context

The PDF pipeline was built for one guide. `scripts/guide-files.sh`,
`build-pdf.sh`, `precommit-build-pdf.sh`, `check-pdf-fresh.sh`, the
pre-commit hook and `make pdf` all name `src/content/harness-guide/` or
`public/harness-guide.pdf`. The chapter order, with a `pagebreak.md` between
chapters, is a hand-kept list. The cover is 40 lines of LaTeX in `cover.md`,
of which five values are specific to the guide. The contents page,
`01-contents.md`, is written and linked by hand. One chapter uses raw LaTeX
for spacing, and the Mermaid diagrams hard-code print colours
(`style X fill:#e8f0ff,…`).

More guides are coming (LLM gateways, then Transformers), converted from
existing PDFs, partly by an agent. The web summaries planned later will read
the same Markdown. A guide's format needs to be written down once, so every
guide follows it and the pipeline can build any of them.

## Decision

A guide is a folder, `src/content/<guide>/`, and adding one needs nothing
else. The format, which `docs/guide-format.md` documents when the pipeline
implements it:

- **Chapters:** numbered Markdown files (`00-intro.md`, `02-…`). The numeric
  prefix sets the order; gaps are allowed. The first file is the
  introduction.
- **Details:** `metadata.yml` holds the title, subtitle, author, co-author
  and an optional date. Pandoc reads it (`--metadata-file`) for the PDF's
  properties and the cover.
- **Cover:** one shared LaTeX template in the pipeline, filled from
  `metadata.yml`. Guides have no `cover.md`.
- **Date:** the date of the guide's last change: today if its files are being
  committed or are uncommitted, otherwise the last commit that touched the
  folder. A `date` in `metadata.yml` overrides it.
- **Page breaks:** the pipeline starts every chapter on a new page. Guides
  have no `pagebreak.md`.
- **Contents:** generated by LaTeX, placed after the introduction. It lists
  every `#` heading after it, and a `##` heading only if it is a main section
  numbered `N.`. Guides have no contents file.
- **Headings:** main sections are numbered `1.`, `2.`, …; appendix sections
  `A.1`, `A.2`, …; bridging or grouping headings ("What's next") are not
  numbered.
- **No raw LaTeX in guide content.** Layout effects use named blocks the
  pipeline supports, starting with `::: spread` (blocks spaced evenly down
  the page).
- **Diagram colours are names, not values:** `sky`, `violet`, `emerald`,
  `coral`, `amber`, `neutral`, applied as Mermaid classes. The pipeline
  defines each name for print (and later for the web, light and dark).
  Diagrams don't use `style` or `fill:`.
- **Filters are Node scripts** run by pandoc (`--filter`), unit-tested with
  Vitest.
- **Output:** `make pdf` builds every guide, `make pdf GUIDE=<guide>` one,
  each to `public/<guide>.pdf`. The pre-commit hook and `make pdf-check`
  cover every guide.

## Alternatives considered

- **An explicit chapter list in `metadata.yml`:** allows any order and file
  name, but bash would need a YAML parser (`yq`), and names could drift from
  the order.
- **A `guide-files.sh` and `cover.md` per guide, as today:** the smallest
  change, but every guide repeats 40 lines of cover LaTeX and a hand-kept
  list.
- **A required `cover.md` in every guide:** lets guides look different, at
  the cost of copying the cover's layout into each and editing them all to
  change it.
- **A hand-written contents page:** full control of its look, but one more
  file to maintain, and to write for every imported guide.
- **A date typed into `metadata.yml`, or the build date:** the first goes
  stale on the first edit; the second changes whenever the PDF is rebuilt,
  with no change to the content.
- **Raw LaTeX allowed sparingly:** works for a PDF-only, hand-written guide,
  but agents converting PDFs would reach for it, each guide would drift into
  its own typesetting, and other readers of the Markdown see noise.
- **Lua or Python filters:** Lua is built into pandoc but would be a
  language nothing else here uses; Python would add a language and a tool.
  Node is already required.
- **Bash text substitution for filters:** matches how `render-diagrams.sh`
  rewrites Mermaid blocks, but can't see document structure (paragraphs,
  lists, nested blocks).
- **Meaning names for diagram colours** (`context`, `constraints`, …): only
  fit the harness guide. **Role names** (`primary`, `positive`, …): vague
  when a diagram has several peers of equal weight. **Hex values mapped by
  the pipeline**, as a web prototype did: fragile, since the same colour is
  spelled several ways.

## Consequences

- **Positive:** a new guide is a folder; covers, page breaks and the
  contents can't be forgotten or drift; a check can enforce the format, so
  agent-written guides stay consistent; one change restyles every guide.
- **Negative:** the harness guide must be migrated: its `cover.md`,
  `pagebreak.md` and `01-contents.md` go, its heuristics page and diagrams
  are rewritten to named blocks and colours. The pipeline gains filters to
  maintain. Viewers that don't know pandoc's fenced divs (GitHub's file
  view) show the `:::` lines as text.
- **Neutral:** the contents page is now LaTeX's (with page numbers) rather
  than a bulleted list, still one page, in the same place. Headings left out
  of the contents also leave the PDF's bookmarks. The harness guide's PDF
  keeps its name, `harness-guide.pdf`, which its folder already gives.
